## Overall assessment

## High

### H1. Commit changes `source_files` before any guard runs and outside a transaction
`apps/api/src/routes/chapters.ts:144-183`
Rejected rows are deleted (165-172) and `bytes` are rewritten (174-176) **before** `enqueueIngest` runs its checks (`chapter_busy` 409, `chapter_has_user_edits` 409). These writes are also not in the `inJobTx` transaction. There is no `status === "draft"` check (presign has one at line 130, commit does not).

Failure scenarios:
- A chapter in `review` that has user edits gets re-committed through the API, and its source objects have been purged (lifecycle) or are unreadable. Every file comes back `missing`, so every `source_files` row is deleted, and then the request returns 400/409. The chapter is now permanently impossible to re-ingest, because the rows are gone even though the request "failed".
- A chapter with an active job (`chapter_busy`) loses its rejected rows even though the response is a 409.

Fix: run the guards first, or move the deletes and updates into the same `inJobTx` after `lockChapter` (for example, add a Phase-3-compatible helper, or re-implement the busy/user-edit checks before mutating). Also reject non-draft chapters unless re-ingest is explicitly intended (`ch.status !== "draft"` → 409), or document that re-ingest of a settled chapter is allowed.

### H2. Thumbnail grid re-signs and re-downloads every full-size page on each `clean_rev` change
`apps/web/src/features/chapter/chapter-page.tsx:44-52` together with `apps/api/src/routes/pages.ts:37`
`pagesSig` includes every page's `clean_rev`. While a 150-page chapter processes, the signature changes almost every 2.5s poll. Each change refetches `/pages`, which presigns all URLs again. The URLs differ (`X-Amz-Date`/signature), so the browser cache misses and every visible `<img>` re-downloads. These are full-resolution cleaned or original pages, not thumbnails. The result is tens of MB every few seconds per open tab, plus MinIO egress. This undercuts the spec's 2–3s progress goal.

Fix: keep a per-page URL map and only replace entries whose `(id, clean_rev)` changed. Alternatively, sign with a time-bucketed date so URLs stay stable inside the TTL window, or add a `?page_ids=` filter to `/pages`. A real thumbnail derivative is a later improvement.

## Medium

### M1. `settings_rev` increment is a read-modify-write that can lose an update
`apps/api/src/routes/series.ts:156-160`
`tx.byId` is a plain SELECT with no `FOR UPDATE`, and then `settingsRev = cur.settingsRev + 1`. Two concurrent PATCHes (say A changes `style_prompt` and B changes `honorific_policy`) both read N and both write N+1.

Failure: a job enqueued between the two commits gets `settings_rev = N+1` with A's settings only. After B commits, the rev is still N+1, so `prepareKey`/`translateKey` (idempotency.ts:19-31) produce the same key, and `insertJob` hands back the stale active job built without B's change. Later cache/idempotency checks also treat the A-only output as current.

Fix: `settingsRev: sql\`${series.settingsRev} + 1\`` (same pattern as `bumpGlossaryRev`), or `SELECT ... FOR UPDATE` before comparing.

### M2. POST policy stays valid after commit, so the magic-byte check is TOCTOU
`chapters.ts:75-77, 157-161`, TTL `MAX_POST_TTL_S` = 15 min.
After commit validates the first 16 bytes, the client can POST again to the same key with the still-valid policy. The Content-Type stays fixed, but the body can be arbitrary, for example HTML or a decompression bomb with a PNG header. Ingest then reads the replaced object.

Impact is limited because the worker decodes images (`worker/mtl_pipeline/images.py`) and the bucket is private. Still, the "server verifies at commit" guarantee does not hold. Fix: record the `ETag` from HEAD at commit and have ingest claim or verify that it is unchanged, or `CopyObject` validated objects to an immutable key that has no outstanding policy.

### M3. Glossary uniqueness is check-then-insert with no DB constraint
`apps/api/src/routes/glossary.ts:57-60, 164-176, 195-213`; schema `packages/db/src/schema/app.ts:228` has only a non-unique index.
Two concurrent creates of the same `source_term`, or a create racing a CSV merge import, both pass `assertUniqueTerm` under READ COMMITTED and insert duplicates. `translateSettings` (enqueue.ts:189) then picks whichever row sorts last, so the glossary becomes nondeterministic, and the UI shows duplicate rows that can no longer be edited cleanly because PATCH fails with `duplicate_term`.

Fix: a unique index on `(workspace_id, coalesce(series_id, '00000000-...'), source_term)` (or `NULLS NOT DISTINCT` on PG15+), with the 23505 error mapped to 409.

### M4. `useChapterLock` cleanup races and stale-closure state
`apps/web/src/features/chapter/use-chapter-lock.ts:39-65`
- Cleanup always fires `unlockChapter`. On remount (React StrictMode is on in `main.tsx:11`, so every dev mount does this) or when `chapterId` or `enabled` changes, the requests go out in the order acquire → DELETE → acquire on separate fetches with no ordering guarantee. If the DELETE lands last, the server shows the lock as free while the UI says `held` for up to 60s, and another user can take it. Phase 5 writes would then get 423.
- An `acquire()` in flight for the previous `chapterId` resolves after a switch and sets `held`/`denied` for the new chapter. State is never reset to `acquiring` when `chapterId` changes.
- After `pagehide` (which includes bfcache), the lock is released but the state stays `held` until the next heartbeat.

Fix: use a per-effect `cancelled` flag or AbortController and ignore results after cleanup. Unlock only if this effect instance acquired. Reset state when `chapterId` changes. Reacquire on `pageshow` when `persisted`. The hook is unused in Phase 4, so fixing it now is cheap.

### M5. Glossary "replace" import wipes the scope with no confirmation, even for an empty CSV
`glossary.ts:196` and `apps/web/src/features/glossary/glossary-editor.tsx:105-124`
A header-only CSV in `replace` mode parses to `entries: []`. The import then deletes every entry in the scope and bumps the rev. The mode select stays sticky on "replace", and choosing a file starts the import immediately.

Fix: a `confirm()` on replace, and/or a server-side 400 when `mode=replace && entries.length === 0`.

## Low
- **L1** CSV export formula injection: `toCsv` (glossary.ts:66-74) does not neutralise cells that start with `= + - @`. Members can plant formulas that run when another member opens the export in Excel. Prefix them with `'`.
- **L2** `validateUploaded` (chapters.ts:48) reports a 0-byte object as `too_large`. Add an `empty` reason.
- **L3** Lock enforcement covers only `commit`. `retry-failed`, `translate` and `cancel` (chapters.ts:217-256) ignore another user's lock. Retranslate respects user state through the page-state writer, so this is arguably fine, but confirm it is intended against the success criterion "API ghi khi không giữ khoá → 423".
- **L4** When the first progress fetch fails (404/403), `status` is undefined, `isChapterSettled(undefined)` returns false, and polling continues every 2.5s against an error (chapter-page.tsx:40). Stop polling when `q.state.status === "error"`.
- **L5** Orphans: rejected objects and abandoned draft chapters (user leaves mid-upload) are never cleaned from MinIO or the DB. Track this for the retention job.
- **L6** In `upload-page.tsx:238`, the rejected list uses `key={r.name}`. Names can repeat across ZIPs, so keys collide. In `upload-queue.ts:21,90`, abort listeners are added on every sleep and attempt and never removed (minor leak). No AbortSignal is wired in, so an upload cannot be cancelled.
- **L7** Sequential statements:
  - chapter create does 400 single-row inserts in one transaction (chapters.ts:101-112). Use a batch `insert().values([...])`.
  - CSV import can run up to 5000 statements.
  - cancel opens one transaction per job, each running `refreshChapter` (O(N²) page reads for 400 pages).
  These are bounded, but slow.
- **L8** The unzip worker has no cap on decompressed size and holds every entry before posting, so a zip bomb or a 200MB ZIP becomes a memory self-DoS (unzip-worker.ts:15-44). Skip entries over 30MB while streaming.
- **L9** There is no JSON body-size limit (`parseJson` → `c.req.json()`; this predates Phase 4). The 2MB glossary CSV cap is enforced only after the full body has been read.
- **L10** The series settings form sends the full object (last write wins over other members' changes). Its `key` includes `settings_rev`, so a background refetch after someone else's save remounts the form and discards unsaved local edits (series-settings-page.tsx:62).
- **L11** `.gitignore` already contains an unresolved merge-conflict block (lines 8-23, `<<<<<<< HEAD` … `>>>>>>> feat/p1-...`). This diff appends below it. It predates Phase 4, but should be fixed before this merges into main.
- **L12** `translationChanged` compares `default_fonts` with `JSON.stringify`, so the same fonts in a different key order count as a change and cause a spurious rev bump (series.ts:103).

## Edge cases checked (no defect found)
- **Keys from other workspaces:** keys are generated by the server (`storageKeys.source(ws, chapter.id, …)`), `source_files` lookups are scoped, and presign checks `chapterId + inArray(ids)` along with a count match.
- **Presign on a non-draft chapter:** returns 409 (line 130), and a test covers it.
- **Concurrent double commit:** `enqueueIngest` locks the chapter `FOR UPDATE` and returns the existing active ingest (`created:false`). Only `chapter.ingest` is enqueued.
- **Cancel loop:** a cascade of prepare cancellations into translate is handled by up to 5 rounds, ingest cancellation returns the chapter to draft, and a test covers it.
- **Glossary bump:** atomic `+1`, same transaction. Workspace scope bumps all series in the workspace (scoped), and a series entry bumps only that series. Tests cover both.
- **CSV parser:** handles BOM, CRLF/LF/CR, `""` escapes, blank lines, unclosed quotes (error), and per-line errors. Unquoted stray quotes are tolerated leniently. In-file duplicates resolve with the last row winning (documented).
- **Lock:** atomic conditional UPDATE (Phase 3). Holder name is limited to workspace members, `is_me` is reported, and commit by a non-holder returns 423 (tested).
- **`lib/api.ts` signature change** (`body` is now JSON-encoded by the client): no remaining callers pass a pre-stringified body. `navigate()` was removed and both callers (login, accept-invite) were migrated. `WorkspaceHomePage` was replaced by `MembersPage` in the router.
- **Tenant isolation:** every new route appears in `RESOURCE_CASES`/`BODIES`. The change is append-only apart from the import line, and the route list comes from the real router.
- **UI ban list:** no gradient, backdrop or blur usage. Status glyphs are arrows only.
- **Phase 5 plug-in:** `editorRoute` sits under `authedRoute` and outside the workspace layout, with typed params. Replacing its component is enough.
